# Magic Square (4×4) — Clean Architecture · Dual-Track UI/Logic TDD 설계 보고서

| 항목 | 내용 |
|------|------|
| 프로젝트 | Magic Square (4×4), TDD 연습용 |
| 목적 | 알고리즘 난이도보다 레이어 분리, 계약 기반 테스트, 리팩토링 훈련 |
| 범위 | 설계·계약·테스트·통합 계획만 (구현 코드 없음) |
| UI 정의 | 실제 화면이 아니라 입력/출력 경계(Boundary) |
| Data | DB 없음 — 저장/로드 인터페이스(메모리/파일 교체 가능) |

## 입력·출력 계약 (고정)

**입력**

- `4×4 int[][]` (0은 빈칸)
- 빈칸은 정확히 2개
- 값 범위: 0 또는 1~16
- 0 제외 중복 금지

**출력**

- `int[6]`
- 좌표는 1-index
- 형식: `[r1,c1,n1,r2,c2,n2]`
- `n1`, `n2`는 두 누락 숫자. (작은수→첫 빈칸, 큰수→둘째 빈칸) 조합이 마방진이면 그 순서, 아니면 반대 순서.

**빈칸 순서 규칙 (고정):** 두 빈칸 `(r_a,c_a)`, `(r_b,c_b)`에 대해 행 우선: `r_a < r_b` 이거나 `(r_a = r_b` 이고 `c_a < c_b)`이면 첫 빈칸은 `(r_a,c_a)`, 둘째는 `(r_b,c_b)`. 내부는 0-index 가능, 출력 직전에만 1-index 변환.

# 1) Logic Layer (Domain Layer) 설계

## 1.1 도메인 개념

| 구분 | 이름 | 책임(SRP) |
|------|------|-----------|
| Value Object | `Grid` (또는 `MagicSquarePuzzle`) | 4×4 정수 배열 캡슐화, 0=빈칸 해석. 크기·인덱스 경계 일관 정의. |
| Value Object | `Cell` | (row, col) 한 칸, 불변. |
| Value Object | `Placement` | (cell, value) 한 번의 배치, 불변. |
| Value Object | `Solution` | 출력 계약 대응: 두 빈칸 순서 + 각 칸 값 `(r1,c1,n1,r2,c2,n2)`. |
| Entity | (선택) `PuzzleState` | 검증 통과 입력 상태 보관 필요 시. 학습용으론 VO 조합만으로도 충분. |
| Domain Service | `EmptyCellFinder` | 값 0인 칸 탐색. |
| Domain Service | `PresentNumberSetAnalyzer` | 비0 값 집합으로 {1..16} 차집합 → 누락 두 수. |
| Domain Service | `MagicSquareValidator` | 완전 채움 4×4 마방진 판정. |
| Domain Service | `TwoHoleSolver` | 빈칸 순서·(n_small, n_large) 두 조합 시도 → `Solution`. |

## 1.2 도메인 불변조건(Invariants)

| ID | Invariant | 검증 시점 |
|----|-----------|-----------|
| INV-GRID-SIZE | 그리드는 항상 4×4. | 모든 공개 도메인 연산 진입 시 |
| INV-EXACTLY-TWO-ZEROS | 값 0인 칸은 정확히 2개. | 입력 정규화 직후 |
| INV-DOMAIN-VALUES | 모든 셀은 {0} ∪ {1..16}. | 입력 정규화 직후 |
| INV-NO-DUP-NONZERO | 0 제외 값은 중복 없음. | 입력 정규화 직후 |
| INV-MAGIC-CONSTANT | 완전 채움에서 행·열·주대각 2개 합 동일(1..16 사용 시 34). | `MagicSquareValidator` 내부 |
| INV-PERMUTATION-WHEN-FILLED | 완전 채움에서 1..16 각 정확히 1회. | `MagicSquareValidator` 내부 |
| INV-SOLUTION-ORDER | 출력 (n1,n2)는 빈칸 순서 및 작은/큰 배치 규칙과 일치. | `TwoHoleSolver` 종료 시 |

## 1.4 Domain API(내부 계약)

구현 코드 없이 메서드 수준만 기술.

| API | 입력 | 출력 | 실패 조건 |
|-----|------|------|-----------|
| `parseOrWrapGrid(raw)` | 4×4 int 이중 구조 | `Grid` | 크기 ≠ 4×4 |
| `assertInputInvariants(grid)` | `Grid` | void 또는 Result | INV-EXACTLY-TWO-ZEROS, INV-DOMAIN-VALUES, INV-NO-DUP-NONZERO 위반 |
| `findEmptyCells(grid)` | `Grid` | 정확히 2개의 `Cell` | (상위에서 invariant 통과 시에만 호출 가능으로 설계 가능) |
| `findMissingTwoNumbers(grid)` | `Grid` | 두 정수 (min, max) | 집합 크기 ≠ 2 |
| `isMagicSquare(filledGrid)` | 0 없는 `Grid` | boolean | — |
| `solveTwoMissing(grid)` | invariant 통과 `Grid` | `Solution` | 두 배치 모두 비마방진 |
| `solutionToContractArray(solution)` | `Solution` | 길이 6 int 배열, 1-index 좌표 | — |

**실패 분류:** `InvalidInputInvariant`, `UnsolvablePuzzle`.

# 2) Screen Layer (UI Layer) 설계 (Boundary Layer)

## 2.1 사용자/호출자 관점 시나리오

| 단계 | 행위 |
|------|------|
| S1 | 호출자가 4×4 행렬을 경계 API에 전달 |
| S2 | 경계가 스키마·개수·범위·중복 검증 |
| S3 | 성공 시 도메인에 위임(Mock 가능) |
| S4 | 도메인 성공 시 `int[6]` 반환 |
| S5 | 실패 시 표준 에러 스키마 반환 |

## 2.2 UI 계약(외부 계약)

**Input schema**

| 필드 | 타입 | 제약 |
|------|------|------|
| `matrix` | int[][] | 길이 4, 각 행 길이 4 |
| 각 원소 | int | 0 또는 1..16 |
| 0의 개수 | — | 정확히 2 |
| 중복 | — | 0 제외 동일 값 없음 |

**Output schema (성공)**

| 필드 | 타입 | 제약 |
|------|------|------|
| `result` | int[6] | `[r1,c1,n1,r2,c2,n2]`, 좌표 1..4, n1≠n2, 1..16 |

**Error schema**

| 필드 | 타입 | 의미 |
|------|------|------|
| `code` | enum 문자열 | 아래 표 코드 |
| `message` | string | 섹션 2.4 고정 문구와 동일 |
| `details` | object | (선택) 테스트에서는 미사용 또는 고정 키만 |

**에러 코드 ↔ 조건**

| code | 발생 조건 |
|------|-----------|
| `ERR_SIZE` | 행 수 ≠ 4 또는 어떤 행 길이 ≠ 4 |
| `ERR_EMPTY_COUNT` | 0의 개수 ≠ 2 |
| `ERR_VALUE_RANGE` | 원소가 0도 아니고 1..16도 아님 |
| `ERR_DUPLICATE` | 비0 값 중복 |
| `ERR_DOMAIN_UNSOLVABLE` | 입력 유효, 도메인 해 없음 |
| `ERR_INTERNAL` | 예기치 않은 오류(Mock 미설정 등) |

## 2.3 UI 레벨 테스트(Contract-first, RED 우선)

| # | 시나리오 | 기대 | Mock |
|---|----------|------|------|

## 2.4 UX/출력 규칙

성공: 기계 판독 `int[6]`. 실패: 아래 문구 **전체 문자열 일치** (대소문자·공백 포함).

| code | message |
|------|---------|
| `ERR_SIZE` | `Input matrix must be 4 by 4.` |
| `ERR_EMPTY_COUNT` | `There must be exactly two empty cells (value 0).` |
| `ERR_VALUE_RANGE` | `Each cell must be 0 or an integer from 1 to 16.` |
| `ERR_DUPLICATE` | `Non-zero values must not repeat.` |
| `ERR_DOMAIN_UNSOLVABLE` | `No valid placement exists for the two missing numbers.` |
| `ERR_INTERNAL` | `Unexpected error.` |

**체크리스트**

- [ ] 모든 UI 테스트가 위 message 전체 assert
- [ ] 동일 조건 → 동일 `code`
- [ ] 검증 순서 고정 시(예: 크기 → 빈칸 개수 → 범위 → 중복) 테스트도 동일 순서 전제 명시

# 3) Data Layer 설계

## 3.1 목적 정의

| 항목 | 내용 |
|------|------|
| 목적 | 마지막 유효 입력·성공 결과 재현, 동일 퍼즐 재실행(학습) |
| 범위 | 메모리 또는 단일 파일 직렬화 DTO |
| 비목표 | 동시성, 다중 사용자, 암호화 |

## 3.2 인터페이스 계약

| 메서드(개념) | 입력 | 출력 | 실패 |
|--------------|------|------|------|
| `saveLastInput(matrixDto)` | UI 통과 4×4 DTO | void | 쓰기 실패 |
| `loadLastInput()` | 없음 | 4×4 DTO 또는 empty | 없음 → empty |
| `saveLastResult(resultDto)` | 길이 6 DTO | void | 쓰기 실패 |
| `loadLastResult()` | 없음 | 길이 6 DTO 또는 empty | 없음 → empty |
| (선택) `clearAll()` | 없음 | void | — |

## 3.3 구현 옵션 비교

| 기준 | A: InMemory | B: File(JSON) |
|------|-------------|---------------|
| 테스트 속도 | 빠름 | 상대적 느림 |
| 재시작 후 유지 | 없음 | 있음 |
| 형식 오류 | 낮음 | 있음 |
| TDD 난이도 | 낮음 | 중간 |

**추천:** 1차 **InMemory**, 통합에서 **File 어댑터**를 포트로 교체해 연습.

**이유:** 도메인·UI 계약이 핵심이므로 I/O 실패를 단계 도입하고, 파일은 별도 어댑터 테스트로 분리.

## 3.4 Data 레이어 테스트

| # | 케이스 | 기대 |

# 4) Integration & Verification

## 4.1 통합 경로 정의

```
Caller → UI Boundary → (Application) → Domain → (Application) → Data(MatrixRepository)
```

**의존성:** UI → (Application) → Domain. Domain은 Data 비의존. Application이 Data 호출.
