## 1. 배경과 비전

### 1.1 문제 인식 (요약)

4×4 격자에 1~16을 한 번씩 배치할 때 행·열·두 주 대각선의 합이 모두 같아야 하는 **마방진**을 다룬다. 본 프로젝트는 “앱 화면”보다 **규칙·불변조건·입출력 계약을 먼저 고정하고, TDD로 검증 가능한 명세로 내리는 것**을 목표로 한다. (상세: `Report/01.MagicSquare_ProblemDefinition_Report.md`)

### 1.2 제품 비전

**Invariant(불변조건) 기반 사고**와 **Dual-Track UI + Logic TDD**를 연습할 수 있는 **학습·측정 가능한** 소프트웨어 자산을 만든다. (Epic: `Report/04.MagicSquare_UserJourney_Epic_To_Technical_Report.md`)

- **UI 트랙(경계):** 호출자·표면(프론트, API, CLI 등)에서 **UX Contract**—오류 문구·코드의 가시성, 정상 시 오류 비가시, 입력 필드 강조 등—으로 RED를 설계한다. 본 PRD에서 그 정본은 §4.5 및 `Report/02` §2.2~2.4·Prompting과 **동일하게 유지되는** 코드·메시지 계약이다.
- **로직 트랙:** **Control + Entity**에서 **Logic Rule**(§4, §5 INV-*)로 RED를 설계한다.
- **MLOps(본 저장소 범위):** 학습용 결정론 솔버를 전제로, **재현성·CI 품질 게이트·(선택) 아티팩트 메타**를 Logic·경계와 같은 “계약”으로 취급한다(§2.4, §7.1, §10).

**GREEN · REFACTOR**는 두 트랙 모두 동일 사이클을 따르며(§6), 파이프라인 실패 시에도 리팩터 정책은 동일하다.

### 1.3 왜 프로그램·TDD인가 (요약)

- 반복 가능한 실행, 판정 자동화, 실수 조기 발견, 규칙을 실행 가능한 형태로 고정. (`Report/01` STEP 3~4)
- 입력·출력·실패가 명확해야 테스트가 의미를 갖고, 회귀와 계약이 통제된다.

### 1.4 Dual-Track 핵심 원리 · 서술 언어(요약)

**원리(한 줄):** UI는 **계약·디자인(UX)**으로 RED를 만들고, 로직은 **규칙·불변**으로 RED를 만든다 — **GREEN**과 **REFACTOR**는 항상 함께 간다.

| UX Contract 언어(경계·UI) | Logic Rule 언어(Control·Entity) |
|-----------------------------|----------------------------------|
| 보인다 / 안 보인다 | 허용한다 / 거부한다 |
| 가능하다 / 불가능하다 | 유지한다 / 중단한다 |
| 활성화 / 비활성화 | 반환한다 / 차단한다 |
| 포함한다 / 포함하지 않는다 | 계산한다 / 저장한다(§7, Control 경유) |

**MLOps 게이트 언어(본 PRD):** 통과한다 / 실패한다(merge 차단), 고정한다(버전·fixture), 재현한다(동일 입력·동일 산출).

## 2. 목표와 성공 기준

### 2.1 비즈니스·학습 목표

1. Invariant 중심 설계(명명된 INV-*와 검증 시점 고정).
2. Dual-Track UI + Logic TDD(ECB, Boundary ↔ Domain 계약 분리; §1.2~1.4).
3. 입력·출력 계약의 명확화 및 테스트와의 1:1 추적.
4. 설계 → 테스트 → 구현 → 리팩터 단계 분리 체화.

### 2.2 측정 가능한 성공 기준 (PRD 수준)

| 구분 | 기준 |
|------|------|
| 도메인 신뢰도 | Domain(entity 등 순수 도메인) 라인 커버리지 ≥ 95% |
| 입력 경계 | 입력 검증 관련 계약·단위 테스트 100% 통과 |
| 코드 품질 | 의미 없는 하드코딩·매직 넘러 남용 없음(명명 상수·설정 집약) |
| 추적성 | INV / 계약 ID ↔ 테스트 ID 매핑 가능 |

(상세 매트릭스: `Report/02.MagicSquare_CleanArchitecture_TDD_Design_Report.md` §4.5)

### 2.3 범위 메모

- **포함:** ECB, 계약 테스트 우선, 리팩터 단계, 커버리지·추적성, §2.4 수준의 MLOps(로컬·CI).
- **비우선(별도 범위):** UI 화면 품질(시각 폴리싱), 온라인 배포·클라우드 MLOps 풀스택, 알고리즘 최적화 경쟁.

### 2.4 MLOps 범위(본 저장소)

본 프로젝트는 **비결정적 모델 서빙**이 아니라 **규칙 기반 솔버**이므로, “MLOps”는 다음 **좁은 정의**로 둔다.

- **품질 게이트:** CI에서 pytest 및 프로젝트 커버리지 정책(§10) 충족을 merge·배포(해당 시) 전 조건으로 삼는다.
- **결정성·재현:** 동일 입력·동일 코드베이스에서 동일 산출(§10 결정성); golden fixture(§9)는 회귀의 **고정 기대값**으로 취급 가능하다.
- **데이터·아티팩트(선택):** §7 저장 포트로 마지막 입력·결과를 남길 때, 파일 어댑터에 **스키마 버전·타임스탬프** 등 최소 메타를 붙이는 것을 허용한다(도메인 비의존 유지).
- **관측성:** `logging` 등 경계 친화적 관측(§10); 운영 대시보드·드리프트 감지는 **비우선(§2.3)**.

## 4. 핵심 제품 요구사항 (기능)

### 4.1 입력 (고정 계약)

- **형식:** `4×4` 정수 격자; `0`은 빈칸.
- **도메인 제약:** 빈칸(`0`)은 **정확히 2개**; 각 칸은 `0` 또는 `1..16`; `0`을 제외한 값은 **중복 없음**.

### 4.2 출력 (고정 계약)

- **형식:** 길이 6의 정수 배열 `int[6]`: `[r1, c1, n1, r2, c2, n2]`.
- **좌표:** **1-index** (1~4).
- **`n1`, `n2`:** 두 누락 숫자. **(작은 수 → 첫 빈칸, 큰 수 → 둘째 빈칸)** 조합이 마방진이면 그 순서; 아니면 **반대 순서**가 계약에 맞는 출력이다.

### 4.3 빈칸 순서 규칙 (고정)

두 빈칸 `(r_a, c_a)`, `(r_b, c_b)`에 대해 **행 우선**: `r_a < r_b` 이거나 `(r_a = r_b` 이고 `c_a < c_b)`이면 첫 빈칸은 `(r_a, c_a)`, 둘째는 `(r_b, c_b)`. 내부는 0-index 가능하나 **출력 직전에만** 1-index 변환.

### 4.4 핵심 동작

1. **입력 검증:** 스키마·불변 위반 시 도메인 솔브로 진행하지 않는다.
2. **빈칸 탐색:** 위 순서로 정확히 2좌표.
3. **누락 수:** `{1..16}`에서 비어 있는 두 수 `(min, max)`.
4. **마방진 판정:** 완전 채움에 대해 행·열·두 주 대각선 합 동일 및 (계약상) 1~16 퍼뮤테이션 검증.
5. **솔브:** 두 배치 시도 후 계약 배열 반환; 둘 다 불가 시 정의된 **불가** 결과(경계 에러 스키마).

### 4.5 경계(외부) 실패 계약 (요약)

호출자 관점에서 크기·빈칸 개수·값 범위·비0 중복·도메인 불가 등에 대해 **안정적인 `code` + 고정 `message`**를 제공한다. 문구·코드 표는 `Report/02` §2.2~2.4 및 Prompting의 UI 계약과 동일하게 유지한다(Breaking 변경 시 프로세스·테스트 정책 준수).

### 4.6 시나리오 매핑: UX Contract · Logic Rule · MLOps 게이트

아래는 대표 시나리오를 **Dual-Track + MLOps** 서술로만 정렬한 것이다. 상세 AC·레벨은 `Report/04`를 따른다.

| 시나리오(요약) | UX Contract(경계·UI) | Logic Rule(Control·Entity) | MLOps 게이트(본 PRD) |
|----------------|------------------------|------------------------------|----------------------|
| 행·열·대각 합 불일치 등 **완전 채움 무효**(L3) | 계약된 **오류 표시 가시**(코드·문구 §4.5) | 합·퍼뮤 검증 **거부**, 솔브 경로 **중단** | 해당 경계·도메인 테스트 **통과** 필수 |
| 빈칸 개수 ≠ 2 등 **스키마 위반** | 해당 **오류 가시** | 빈칸 탐색·솔브 **차단** | 입력 계약 테스트 **통과** 필수 |
| **정상 솔브**(§9 fixture 등) | (UI 정의 시) 완료·결과 **가시** | `int[6]` **반환** | golden 기대값 회귀 **통과** |
| **비정수·범위 외 입력**(L2 등) | 필드 **오류 강조 가시**(UI 정의 시) | 입력 **차단**, Entity 미진입 | 경계 검증 테스트 **통과** 필수 |
| 마지막 유효 입력·결과 **저장**(§7) | (선택) 저장 완료 **가시** | Control이 저장 포트 호출 **허용** | 저장 스키마·(선택) 메타 **고정** |

## 6. 아키텍처·구현 원칙 (요구사항)

- **패턴:** ECB(Entity–Control–Boundary). 의존: `boundary → control → entity` 단방향.
- **언어·품질:** Python 3.10+, PEP 8, 타입 힌트·Google 스타일 docstring(public), 줄 길이 88.
- **TDD:** RED → GREEN → REFACTOR; 금지 사항·테스트 정책은 루트 `.cursorrules` 및 `Report/03.MagicSquare_CursorRules_Report.md`와 일치.

---

## 7. 데이터·통합 (선택·단계적)

- **목적:** 마지막 유효 입력·결과 재현(학습).
- **1차:** InMemory 저장소; **통합/연습:** 파일(JSON 등) 어댑터로 교체 가능한 포트.
- Domain은 저장소에 **비의존**; Application/Control이 저장 호출. (`Report/02` §3~4)

### 7.1 MLOps와의 정렬

- **역할:** §7 저장물과 §9 fixture는 “학습 재현”을 위한 **로컬 아티팩트**로 보며, 클라우드 모델 레지스트리·온라인 드리프트 감지는 §2.3 **비우선**이다.
- **게이트:** CI에서 테스트·커버리지(§10)를 만족하지 못하면 본 저장소 정책상 **통합 실패**로 간주한다(§2.4).
- **결정성:** 솔버·검증 로직에 RNG를 두지 않으며, 회귀 테스트는 §9 기대값과 **고정 비교**한다.

## 12. 용어

- **마방진(본 PRD):** 4×4, 1~16 각 1회, 네 행·네 열·두 주 대각선 합이 모두 동일.
- **빈칸:** 값 `0`.
- **계약:** 본 문서 §4 및 `Report/02`의 스키마·에러 표와 동일 해석.
- **Dual-Track UI + Logic TDD:** UI 트랙은 경계에서 **UX Contract**로, 로직 트랙은 **Control·Entity**에서 **Logic Rule**로 RED를 설계하고, GREEN·REFACTOR는 공통 사이클(§1.2~1.4, §6).
- **UX Contract:** 보임/가능/활성 등 **호출자·표면** 관점의 상태·문구·동작 약속(§4.5 정본).
- **Logic Rule:** 허용/거부/반환/차단 등 **도메인·유스케이스** 관점의 규칙(§4, §5).
- **MLOps(본 PRD):** §2.4의 좁은 정의 — CI 품질 게이트, 결정성·재현, (선택) 저장·fixture 메타; 클라우드 MLOps 전부를 뜻하지 않는다.
