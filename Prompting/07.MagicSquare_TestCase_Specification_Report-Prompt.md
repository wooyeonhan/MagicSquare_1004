## 추천 브랜치 정책 (README 중심)

### 1. 기본 줄기
- **`main`**: 항상 배포·공유 가능한 상태(문서도 “읽을 수 있는 최신”으로 유지).
- **작업은 `main`에서 직접 하지 않고** 짧은 수명 브랜치에서 하기를 권장합니다. README만 바꿔도 히스토리·리뷰가 분리됩니다.

### 2. 브랜치 이름
- 문서만: `docs/readme-<한줄요약>` (예: `docs/readme-todo-section`)
- PRD·리포트와 같이 묶을 때: `docs/update-onboarding`
- 나중에 코드까지: `feat/...`, `fix/...`로 구분

### 3. 수명·병합
- **1인·소규모**: `docs/...` → PR(또는 짧은 self-review) → `main` merge. 커밋 메시지는 README에 맞게 `docs:` 접두를 유지하면 좋습니다.
- **급한 오타 1줄**만: 예외적으로 `main` 직접 커밋도 가능하지만, 습관은 브랜치로 통일하는 편이 안전합니다.

### 4. 원격 정리 (중요)
- 지금처럼 **canonical 저장소를 하나 정해** 두는 것이 정책의 핵심입니다. 예: 일상 작업은 `wooyeonhan`만 `git push`, `kzfornetwork`는 포크 동기화용 등.
- `main`에 merge한 뒤 **어느 원격에 push할지**를 README나 팀 규칙에 한 줄이라도 적어 두면 혼선이 줄어듭니다.

### 5. `main` 보호 (선택)
- GitHub에서 **PR 필수**, **직접 push 금지**는 협업·외부 기여가 있을 때만 강하게 권장합니다.
- 혼자면 **선택**이고, 대신 “항상 브랜치 → merge”만 지켜도 충분한 경우가 많습니다.

### 6. 코드 스캐폴딩 이후
- README와 무관한 구현은 `feat/...`로 분리하고, **한 PR에 문서 대량 수정 + 대규모 리팩터**를 섞지 않는 것이 리뷰에 유리합니다.
