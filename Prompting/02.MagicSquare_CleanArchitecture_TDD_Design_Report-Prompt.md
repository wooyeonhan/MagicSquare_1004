**User**

당신은 Dual-Track UI + Logic TDD 및 Clean Architecture 설계 전문가입니다.

프로젝트: Magic Square (4x4) — TDD 연습용
목적: 알고리즘 난이도보다 “레이어 분리 + 계약 기반 테스트 + 리팩토링” 훈련
제약:
- 구현 코드는 작성하지 마십시오. (설계/계약/테스트/통합 계획만)
- UI는 실제 화면이 아니라 “입력/출력 경계(Boundary)”로 정의
- Data Layer는 DB가 아니라 “저장/로드 인터페이스(메모리/파일 교체 가능)” 수준만
- 입력/출력은 명확히 고정

입력 계약:
- 4x4 int\\\[]\\\[] (0은 빈칸)
- 빈칸은 정확히 2개
- 값 범위: 0 또는 1\\\~16
- 0 제외 중복 금지
출력 계약:
- int\\\[6]
- 좌표는 1-index
- 반환 형식: \\\[r1,c1,n1,r2,c2,n2]
- n1,n2는 두 누락 숫자이며, (작은수→첫빈칸, 큰수→둘째빈칸) 조합이 마방진이면 그 순서로, 아니면 반대로

# 1) Logic Layer (Domain Layer) 설계

## 1.1 도메인 개념

| 구분 | 이름 | 책임(SRP) |
|------|------|-----------|
| Value Object | `Grid` (또는 `MagicSquarePuzzle`) | 4×4 정수 배열을 캡슐화하고, “0=빈칸” 해석만 담당. 크기·인덱스 경계는 여기서 일관되게 정의(내부 0-index 권장, 외부 계약과 변환은 경계에서). |
| Value Object | `Cell` | (row, col) 한 칸. 불변. |
| Value Object | `Placement` | (cell, value) 한 번의 배치. 불변. |
| Value Object | `Solution` | 출력 계약과 대응: 두 빈칸 순서 + 각 칸에 넣을 값 `(r1,c1,n1,r2,c2,n2)` (좌표 의미는 “빈칸 순서”와 동일). |
| Entity | (선택) `PuzzleState` | “검증 통과한 입력 상태”를 식별자 없이 보관할 필요가 있으면 사용. 학습용으론 Value Object 조합만으로도 충분. |
| Domain Service | `EmptyCellFinder` | 그리드에서 값이 0인 칸을 정확히 찾아 개수·위치 반환. |
| Domain Service | `PresentNumberSetAnalyzer` | 0이 아닌 셀의 값 집합으로부터 “누락된 두 수” 후보를 {1..16} 차집합으로 산출. |
| Domain Service | `MagicSquareValidator` | 완전히 채워진 4×4가 마방진인지 판정(행/열/대각선 합·1..16 사용 여부). |
| Domain Service | `TwoHoleSolver` | 두 빈칸의 순서(선행/후행)와 (n_small, n_large) 두 조합을 시도해 `Solution` 결정. |

## 1.2 도메인 불변조건(Invariants)

| ID | Invariant | 검증 시점 |
|----|-----------|-----------|
| INV-GRID-SIZE | 그리드는 항상 4×4이다. | 모든 공개 도메인 연산 진입 시 |
| INV-EXACTLY-TWO-ZEROS | 값이 0인 칸은 정확히 2개이다. | 입력 정규화 직후 |
| INV-DOMAIN-VALUES | 모든 셀 값은 {0} ∪ {1..16}이다. | 입력 정규화 직후 |
| INV-NO-DUP-NONZERO | 0을 제외한 값은 서로 다르다(중복 없음). | 입력 정규화 직후 |
| INV-MAGIC-CONSTANT | 완전 채움 상태에서 각 행·열·주대각 2개의 합은 동일하다(4×4, 1..16 사용 시 상수 34). | `MagicSquareValidator` 내부 |
| INV-PERMUTATION-WHEN-FILLED | 완전 채움 상태에서 1..16이 각각 정확히 1회 등장한다. | `MagicSquareValidator` 내부 |
| INV-SOLUTION-ORDER | 출력의 (n1,n2)는 “첫 빈칸·둘째 빈칸” 순서와 일치하며, (작은수→첫, 큰수→둘)이 마방진이면 그 순서, 아니면 반대 순서이다. | `TwoHoleSolver` 종료 시 |

## 1.3 핵심 유스케이스(도메인 관점)

| UC-ID | 이름 | 전제 | 결과 |
|-------|------|------|------|
| UC-01 | 빈칸 찾기 | INV-GRID-SIZE | 0인 칸 좌표 목록(내부 표현) |
| UC-02 | 누락 숫자 찾기 | INV-DOMAIN-VALUES, INV-NO-DUP-NONZERO | {1..16}에서 제외된 정확히 2개의 수(정렬: 작은 수, 큰 수) |
| UC-03 | 마방진 판정 | 그리드에 0이 없음 | 참/거짓 + (선택) 실패 이유 분류 |
| UC-04 | 두 조합 시도 | 빈칸 2개의 순서가 정해짐, 누락 두 수가 정해짐 | 마방진이 되는 배치가 있으면 `Solution`, 없으면 도메인 실패 |
| UC-05 | 빈칸 순서 고정 규칙 | 빈칸 2개 | 도메인 규칙으로 순서를 단일하게 정의(예: 행 우선, 같으면 열 우선) — **구현 없이 규칙만 고정** |

**빈칸 순서 고정 규칙(모호성 제거):**  
`(r_a,c_a)`와 `(r_b,c_b)`가 0인 칸일 때, `r_a < r_b` 이거나 `(r_a = r_b 이고 c_a < c_b)` 이면 첫 빈칸은 `(r_a,c_a)`, 둘째는 `(r_b,c_b)`. 내부 인덱스가 0-base이면 출력 직전에만 1-base로 변환.

## 1.4 Domain API(내부 계약)

| API | 입력 | 출력 | 실패 조건 |
|-----|------|------|-----------|
| `parseOrWrapGrid(raw)` | 4×4 int 이중 구조 | `Grid` | 크기 ≠ 4×4 |
| `assertInputInvariants(grid)` | `Grid` | void 또는 Result | INV-EXACTLY-TWO-ZEROS, INV-DOMAIN-VALUES, INV-NO-DUP-NONZERO 중 하나라도 위반 |
| `findEmptyCells(grid)` | `Grid` | 정확히 2개의 `Cell` | (위반 시 상위에서 이미 거부했다면 호출 불가로 설계 가능) |
| `findMissingTwoNumbers(grid)` | `Grid` | 두 정수 (min, max) | 집합 크기가 2가 아니면 실패 |
| `isMagicSquare(filledGrid)` | 0 없는 `Grid` | boolean | — |
| `solveTwoMissing(grid)` | invariant 통과 `Grid` | `Solution` | 두 배치 모두 마방진이 아니면 실패 |
| `solutionToContractArray(solution)` | `Solution` | 길이 6의 int 배열, 1-index 좌표 | — |

**실패 분류(도메인):**  
- `InvalidInputInvariant` (전제 위반)  
- `UnsolvablePuzzle` (두 조합 모두 비마방진)

## 1.5 Domain 단위 테스트 설계(RED 우선)

| # | 케이스 유형 | 내용 | 보호하는 Invariant |
|---|-------------|------|-------------------|
| D-01 | 정상 | 알려진 해가 있는 4×4, 빈칸 2, 나머지 유효 | INV-SOLUTION-ORDER, INV-MAGIC-CONSTANT |
| D-02 | 정상 | (작은→첫, 큰→둘)이 성공하는 패턴 | INV-SOLUTION-ORDER |
| D-03 | 정상 | 위가 실패하고 반대 순서(n1,n2 swap)만 성공하는 패턴 | INV-SOLUTION-ORDER |
| D-04 | 비정상 | 0이 1개만 | INV-EXACTLY-TWO-ZEROS |
| D-05 | 비정상 | 0이 3개 | INV-EXACTLY-TWO-ZEROS |
| D-06 | 비정상 | 0이 아닌 값이 17 | INV-DOMAIN-VALUES |
| D-07 | 비정상 | 0이 아닌 값이 -1 | INV-DOMAIN-VALUES |

| D-10 | 비정상 | 수학적으로 두 배치 모두 불가능한 퍼즐 | Unsolvable |
| D-11 | 단위 | `isMagicSquare`만: 완전 채움 마방진 참 | INV-MAGIC-CONSTANT, INV-PERMUTATION-WHEN-FILLED |
| D-12 | 단위 | `isMagicSquare`: 합은 맞지만 1..16 퍼뮤테이션이 아닌 경우 거짓 | INV-PERMUTATION-WHEN-FILLED |

# 2) Screen Layer (UI Layer) 설계 (Boundary Layer)

## 2.1 사용자/호출자 관점 시나리오

| 단계 | 행위 |
|------|------|
| S1 | 호출자가 4×4 행렬(원시 구조)을 경계 API에 전달 |
| S2 | 경계가 스키마·개수·범위·중복 검증 |
| S3 | 성공 시 도메인 서비스에 위임(여기서는 Mock 가능) |
| S4 | 도메인 성공 시 `int[6]`을 그대로 또는 동일 계약으로 반환 |
| S5 | 실패 시 표준 에러 스키마로 반환 |

## 2.2 UI 계약(외부 계약)

**Input schema**

| 필드 | 타입 | 제약 |
|------|------|------|
| `matrix` | int[][] | 길이 4, 각 행 길이 4 |
| 각 원소 | int | 0 또는 1..16 |
| 0의 개수 | — | 정확히 2 |
| 중복 | — | 0 제외 동일 값 없음 |

**Output schema (성공)**

| 필드 | 타입 | 제약 |
|------|------|------|
| `result` | int[6] | `[r1,c1,n1,r2,c2,n2]`, 모든 좌표 1..4, n1,n2는 1..16 서로 다름 |

**Error schema**

| 필드 | 타입 | 의미 |
|------|------|------|
| `code` | enum 문자열 | 아래 표의 코드 중 하나 |
| `message` | string | 아래 2.4의 고정 문구와 동일 |
| (선택) `details` | object | 테스트에서는 사용하지 않거나 고정 키만 허용 |

**에러 코드 ↔ 조건 (검증 가능)**

| code | 발생 조건 |
|------|-----------|
| `ERR_SIZE` | 행 수 ≠ 4 또는 어떤 행의 길이 ≠ 4 |
| `ERR_EMPTY_COUNT` | 0의 개수 ≠ 2 |
| `ERR_VALUE_RANGE` | 어떤 원소도 `0`도 아니고 `1..16`도 아님 |
| `ERR_DUPLICATE` | 0이 아닌 값이 2회 이상 등장 |
| `ERR_DOMAIN_UNSOLVABLE` | 입력은 유효하나 도메인이 해 없음 |
| `ERR_INTERNAL` | 예기치 않은 오류(테스트에서는 Mock 미설정 등에 한해 사용) |

## 2.3 UI 레벨 테스트(Contract-first, RED 우선)

| # | 시나리오 | 기대 | Mock 가정 |
|---|----------|------|------------|
| U-01 | 3×4 입력 | `ERR_SIZE`, 고정 message | 도메인 미호출 |
| U-02 | 4×4이나 한 행 길이 3 | `ERR_SIZE` | 도메인 미호출 |
| U-03 | 빈칸 1개 | `ERR_EMPTY_COUNT` | 도메인 미호출 |
| U-04 | 빈칸 3개 | `ERR_EMPTY_COUNT` | 도메인 미호출 |
| U-05 | 원소 17 포함 | `ERR_VALUE_RANGE` | 도메인 미호출 |
| U-06 | 비0 중복 | `ERR_DUPLICATE` | 도메인 미호출 |
| U-07 | 유효 입력, Mock이 `[1,2,3,4,5,6]` 반환 | 응답 배열 동일, 길이 6 | 도메인 1회 호출 |
| U-08 | 유효 입력, Mock이 Unsolvable throw | `ERR_DOMAIN_UNSOLVABLE` | 도메인 1회 호출 |
| U-09 | 성공 응답 각 원소 타입 int, 길이 6 | 스키마 검증 | Mock 고정값 |
| U-10 | 좌표가 1..4 범위 밖이면(도메인 버그 시뮬레이션) | `ERR_INTERNAL` 또는 경계에서 “출력 검증 실패” 정책을 문서화한 코드로 처리 | 선택 정책을 한 가지만 채택해 테스트에 명시 |

## 2.4 UX/출력 규칙

**원칙:** 성공 시에는 기계 판독 가능한 `int[6]`만 반환해도 됨. 실패 시에만 메시지 고정.

**고정 문구 (정확히 일치, 대소문자·공백 포함)**

| code | message (고정 문자열) |
|------|------------------------|
| `ERR_SIZE` | `Input matrix must be 4 by 4.` |
| `ERR_EMPTY_COUNT` | `There must be exactly two empty cells (value 0).` |
| `ERR_VALUE_RANGE` | `Each cell must be 0 or an integer from 1 to 16.` |
| `ERR_DUPLICATE` | `Non-zero values must not repeat.` |
| `ERR_DOMAIN_UNSOLVABLE` | `No valid placement exists for the two missing numbers.` |
| `ERR_INTERNAL` | `Unexpected error.` |

**체크리스트**

- [ ] 모든 UI 테스트가 위 문구 전체 문자열을 assert  
- [ ] 동일 조건에서는 동일 `code`만 반환  
- [ ] 검증 순서를 문서에 고정하면(예: 크기 → 빈칸 개수 → 범위 → 중복) 그 순서대로 RED 테스트 작성

# 3) Data Layer 설계 (Data Layer)

## 3.1 목적 정의

| 항목 | 내용 |
|------|------|
| 목적 | 마지막 유효 입력·마지막 성공 결과를 재현하거나, 학습용으로 “동일 퍼즐 재실행”을 지원 |
| 범위 | DB 없음. 프로세스 내 메모리 또는 단일 파일에 직렬화 가능한 DTO 수준 |
| 비목표 | 동시성, 다중 사용자, 암호화 |

## 3.2 인터페이스 계약

| 메서드(개념) | 입력 | 출력 | 실패 |
|--------------|------|------|------|
| `saveLastInput(matrixDto)` | UI가 통과시킨 4×4 DTO | void | 저장소 쓰기 실패 |
| `loadLastInput()` | 없음 | 4×4 DTO 또는 empty | 데이터 없음 → 명시적 empty |
| `saveLastResult(resultDto)` | 길이 6 int 배열 DTO | void | 쓰기 실패 |
| `loadLastResult()` | 없음 | 길이 6 DTO 또는 empty | 데이터 없음 |
| (선택) `clearAll()` | 없음 | void | — |

**저장 대상:** 입력 행렬(필수), 실행 결과(선택이지만 학습상 권장).

## 3.3 구현 옵션 비교

| 기준 | 옵션 A: InMemory | 옵션 B: File(JSON) |
|------|------------------|---------------------|
| 테스트 속도 | 빠름 | 상대적으로 느림 |
| 프로세스 재시작 후 유지 | 없음 | 있음 |
| 형식 오류 가능성 | 낮음 | 있음 |
| TDD 난이도 | 낮음 | 중간 |

**추천:** **옵션 A (InMemory)를 1차 구현**, 통합 테스트에서만 **옵션 B를 어댑터로 교체**하는 식의 포트/어댑터 연습.

**이유:** 도메인·UI 계약이 핵심 학습 목표이므로 I/O 실패를 단계적으로 도입하고, 파일은 별도 어댑터 테스트로 분리해 실패 원인 추적 비용을 줄임.

## 3.4 Data 레이어 테스트

|---|--------|------|

# 4) Integration & Verification (통합 및 검증)

## 4.1 통합 경로 정의

```
[Caller]
   ↓
[UI Boundary]  — 검증(Input/Error schema)
   ↓ (optional)
[Application / UseCase Orchestrator]  — “검증된 입력 → Domain → 결과/저장” 순서 고정
   ↓
[Domain]  — invariant + solve
   ↓ (optional callback)
[Data: MatrixRepository]  — save/load
```

**의존성 방향:** UI → (Application) → Domain; Data는 인터페이스로만 참조되며 Domain은 Data를 알지 않음. Application이 Data를 호출하는 구조가 Clean Architecture에 맞음.

## 4.2 통합 테스트 시나리오

**정상 (2개 이상)**

| ID | 설명 |
|----|------|
| I-OK-01 | 유효 행렬 → 실제 도메인 → `int[6]`이 계약과 일치(좌표 1..4, n 중복 없음) |
| I-OK-02 | 동일 입력 두 번 → 동일 출력(결정적) |
| I-OK-03 | (선택) 성공 후 `saveLastInput` / `saveLastResult` 호출 → load 일치 |

**실패 (3개 이상)**

| ID | 설명 |
|----|------|
| I-FAIL-01 | UI 경계에서 크기 오류 → 도메인 미실행 |
| I-FAIL-02 | UI 통과 입력이지만 퍼즐 불가 → `ERR_DOMAIN_UNSOLVABLE` |
| I-FAIL-03 | Data 파일 어댑터: 손상 파일 → 정의된 저장소 오류 처리 |
| I-FAIL-04 | (선택) Application이 저장 실패를 사용자에게 매핑하는 정책이 있으면 그 경로 1건 |

## 4.3 회귀 보호 규칙

| 규칙 | 내용 |
|------|------|
| R-01 | `int[6]` 순서·의미·1-index 좌표 계약 변경 시 **버전 필드** 또는 **별도 API**로만 확장 |
| R-02 | 에러 `code`·`message` 변경은 **Breaking change**로 취급, 테스트 먼저 수정 금지(의도적 릴리스 프로세스) |
