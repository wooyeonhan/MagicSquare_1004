To-Do 리스트를 어떤 깊이로 쓰느냐에 따라 참조 문서를 나누면 됩니다.

## 1차로 쓰기 좋은 것: `docs/PRD.md`

**구현·검증 단위 작업 목록**을 만들 때는 여기가 가장 적합합니다. PRD 자체가 “구현·테스트·리뷰의 단일 기준선”이라고 적혀 있고, 섹션별로 할 일이 잘 나뉘어 있습니다.

| PRD 섹션 | To-Do에 쓰는 방식 |
|-----------|-------------------|
| §2 목표·성공 기준 | 마일스톤·완료 조건(커버리지, 계약 테스트 등) |
| §2.3 범위 | “하지 않을 일” 체크로 스코프 고정 |
| §4 핵심 요구·§5 INV-* | 기능·불변별 태스크, 테스트와 1:1 매핑 |
| §6 아키텍처·TDD | ECB 구조, RED→GREEN→REFACTOR 순서 |
| §7·§10 | 저장·CI·NFR 항목이 필요할 때만 항목 추가 |
| §8 사용자 스토리 요약 | 상위 Epic/스토리 단위 체크리스트 |

즉, **“무엇을 만들고, 어떤 계약으로 끝내면 되는지”**는 `docs/PRD.md`만으로도 To-Do의 뼈대를 잡을 수 있습니다.

## 세부 작업·시나리오까지 쪼갤 때: `Report/04`

PRD §8·§9에 나온 대로, **상세 수용 기준(AC), Gherkin, fixture 기대값**은 `Report/04.MagicSquare_UserJourney_Epic_To_Technical_Report.md`에 있습니다.  
“스토리별로 테스트 케이스까지 To-Do에 넣고 싶다”면 **PRD의 스토리 줄기 + Report/04의 Level 3~4**를 같이 보는 구성이 맞습니다.

## 계약·레이어·에러 코드까지 맞출 때: `Report/02`

입출력·경계 실패·레이어링을 **코드/테스트 이름 수준**으로 쪼개려면 `Report/02.MagicSquare_CleanArchitecture_TDD_Design_Report.md`를 참조하는 게 좋습니다. PRD §4.5·§11에서도 여기를 정본으로 가리킵니다.

## 코딩 규칙·금지 사항: `Report/03`, `.cursorrules`

“리팩터 전에 지켜야 할 규칙”, 테스트 정책 같은 **공정 To-Do**는 `Report/03`과 루트 `.cursorrules`가 맞습니다.

## `Report/05`와 `Prompting/05`

- **`Report/05.MagicSquare_PRD_Report.md`**: PRD 메타·갱신 요약과 `docs/PRD.md` 동기 본문이라, **PRD와 동일한 내용**이 대부분입니다. To-Do 소스로는 **`docs/PRD.md` 한 곳**만 써도 됩니다.  
- **`Prompting/05...`**: PRD 구성 가이드·Dual-Track 대화 로그에 가깝습니다. **문서 구조나 방법론**을 To-Do에 넣을 때 보조 참고용이지, 기능 단위 할 일 목록의 정본은 아닙니다.
