## Level 1 — Epic (비즈니스 목표)

### EPIC — Business Goal

**Epic:** Invariant(불변조건) 기반 사고 훈련 시스템 구축  

4×4 Magic Square(빈칸 2개, `int[6]` 출력 계약)를 **연습 도메인**으로 삼아, 소프트웨어를 “규칙이 먼저, 검증이 따라오고, 구현은 그 뒤”로 만드는 습관을 제품 수준이 아니라 **학습·측정 가능한 시스템**으로 고정하는 것이 이 Epic의 비즈니스 목표다.

---

### 목적

4×4 Magic Square 문제를 활용하여 다음을 달성한다.

1. **Invariant 중심 설계 사고 훈련**  
   도메인 불변조건(예: `INV-GRID-SIZE`, `INV-EXACTLY-TWO-ZEROS`, `INV-DOMAIN-VALUES`, `INV-NO-DUP-NONZERO`, `INV-SOLUTION-ORDER` 등)을 명시하고, API·유스케이스·검증 시점과의 대응을 설계 단계에서 먼저 말로·표로 고정한 뒤 코드로 내린다.

2. **Dual-Track TDD 적용 훈련**  
   Logic Track(도메인·INV 보호)과 Boundary Track(입력/출력 계약, DTO·프레젠테이션)을 분리해 RED → GREEN → REFACTOR를 각 트랙에서 반복하고, 레이어 간 의존 방향(ECB: Boundary → Control → Entity)을 지킨다.

3. **입력/출력 계약 명확화 훈련**  
   입력(`4×4`, 0=빈칸 정확히 2개, 1~16 및 중복 규칙)과 출력(`int[6]`, 1-index, 빈칸 순서·누락 두 수 배치 규칙)을 실행 가능한 테스트와 타입·함수 시그니처로 동일하게 유지한다.

4. **설계 → 테스트 → 구현 → 리팩토링 흐름 체화**  
   설계 보고서·계약 테스트가 “진실의 원천”이 되고, 구현은 그에 맞추며, 리팩터링은 동작을 바꾸지 않고 구조만 개선하는 단계로 구분해 반복한다.

### 성공 기준

| 구분 | 기준 | 측정/근거 |
|------|------|-----------|
| 도메인 신뢰도 | **Domain Logic 라인 커버리지 ≥ 95%** | `entity`(및 순수 도메인에 해당하는 모듈) 기준 커버리지 리포트 |
| 입력 경계 | **입력 검증 100% 계약 테스트 통과** | INV 위반 케이스(크기, 0 개수, 도메인 값, 비0 중복 등)에 대한 계약/단위 테스트 전부 GREEN |
| 표현 일관성 | **의미 없는 하드코딩 없음** | “한 번만 쓰이는 숫자/문자열”은 명명된 상수·설정·Enum 등으로 한곳에 모음 |
| 유지보수성 | **매직 넘버 없음** | 격자 크기·매직 합·16·좌표 체계 등은 도메인 상수/설정으로만 참조 |
| 추적성 | **Invariant → Test 추적 가능** | 각 INV(또는 계약 ID)마다 대응 테스트 ID·주석·문서 표(예: 설계 보고서의 INV–테스트 매핑)가 존재하고, 역으로 테스트에서 어떤 INV를 지키는지 식별 가능 |

## Level 2 — User Journey (사용자 여정)

### Persona

| 항목 | 설명 |
|------|------|
| **역할** | 소프트웨어 개발 학습자 |
| **맥락** | TDD 훈련 중 — RED → GREEN → REFACTOR를 의식적으로 반복한다. |
| **배경** | Clean Architecture 이해 중 — 경계(Boundary)·유스케이스(Control)·도메인(Entity)의 책임과 의존 방향을 코드로 확인하고 싶다. |

**여정의 목표:** “마방진 앱 하나 완성”이 아니라, **계약·불변조건·트랙 분리**를 몸에 익히는 것이다.

---

### Journey

#### Step 1 — 문제 인식

“마방진을 구현한다”가 아니라, 다음을 먼저 분해한다.

- **무엇을** 완성 상태로 볼 것인가(4×4, 1~16, 행·열·대각 합 동일 등).
- **입력으로 무엇이 주어지는가**(예: 빈칸 2개, 나머지 고정).
- **출력은 무엇인가**(예: 계약된 `int[6]`, 좌표 체계, 빈칸·누락 수 순서 규칙).
- **실패는 어떤 종류로 구분할 것인가**(입력 불변 위반 vs 해 없음 등).

이 단계에서 “구현 언어·프레임워크”보다 **판정 가능한 문장**이 우선이다.

---

#### Step 2 — 계약 정의

실행 가능한 명세로 고정한다.

1. **입력 스키마 정의**  
   크기(4×4), `0`=빈칸의 개수·위치 해석, 허용 값 집합(0 ∪ 1~16), 비0 중복 금지 등을 표·문서·테스트 이름으로 명시한다.

2. **출력 스키마 정의**  
   길이·타입(예: `int[6]`), 1-index 좌표, 두 누락 수와 빈칸 순서(행 우선 등)의 대응 규칙을 한 가지 해석으로만 고정한다.

3. **예외 정책 정의**  
   계약 위반(불변조건 실패)과 “입력은 유효하나 해가 없음”을 타입·메시지·HTTP/CLI 경계에서 어떻게 구분·전달할지 정책을 정한다.

이 단계 산출물이 이후 모든 RED 테스트의 **Arrange·Assert 기준**이 된다.

---

#### Step 3 — Domain 분리

도메인 책임을 **서로 다른 이유로 바뀌지 않게** 나눈다.

| 구성 요소 | 역할(요약) |
|-----------|------------|
| **BlankFinder** | 값이 비어 있는 칸(0)의 위치를 찾는다. 빈칸 개수·순서 규칙과 맞물린다. |
| **MissingNumberFinder** | 이미 놓인 수로부터 {1..16}에서 빠진 두 수를 찾는다. |
| **MagicSquareValidator** | 완전히 채운 격자가 마방진 정의(합·퍼뮤테이션 등)를 만족하는지 판정한다. |
| **Solver** | 빈칸 순서·누락 두 수의 배치 조합을 시도하고, 출력 계약에 맞는 해를 조합하거나 실패를 반환한다. |

Control 층은 이들을 **오케스트레이션**만 하고, Boundary는 입출력 변환만 담당한다(ECB).

---

#### Step 4 — Dual-Track 진행

경계와 로직을 **동시에** 계약으로 밀어 넣는다.

1. **UI RED / Logic RED 병렬**  
   - **Logic Track:** `BlankFinder`, `MissingNumberFinder`, `Validator`, `Solver` 단위·도메인 계약 RED.  
   - **UI(경계) Track:** 파싱·검증 실패·성공 응답 형식에 대한 RED(실제 화면이 아니어도 Boundary 어댑터 수준으로 정의 가능).

2. **GREEN 최소 구현**  
   각 트랙에서 **방금 실패한 테스트만** 통과시키는 최소 코드만 추가한다. 트랙 간에는 필요한 DTO·유스케이스 호출만 연결한다.

3. **REFACTOR 통합 정리**  
   테스트가 모두 녹색인 상태에서 이름·중복 제거·파일 위치·의존 방향을 정리한다. 동작·계약은 바꾸지 않는다.

---

#### Step 5 — 회귀 보호

앞으로의 변경이 계약을 깨지 않도록 **의도된 실패**를 테스트로 남긴다.

- **엣지 케이스 추가**  
  빈칸이 같은 행/열/대각 근처, 경계 인덱스 등 레이아웃 다양성.

- **입력 오류 케이스 추가**  
  크기 오류, 0 개수 오류, 도메인 밖 값, 비0 중복 등 — 각각 대응 불변조건(INV)과 매핑해 둔다.

- **조합 실패 케이스 추가**  
  입력은 유효하나 두 배치 모두 비마방진인 경우 등, Solver·Validator와 연결된 실패 경로.

이 단계까지 오면 **“Invariant → Test” 추적**과 **회귀 안전망**이 사용자 여정의 종착역에 해당한다.

## Level 3 — User Stories

### Story 1 — 입력 검증

**As a** 학습자  
**I want to** 격자 입력이 도메인 불변조건을 만족하는지 경계(또는 Control 정규화)에서 검증되길 원한다  
**So that** 잘못된 데이터가 Entity 계층으로 넘어가지 않고, 실패 원인이 계약 위반으로 명확히 남는다  

**Acceptance Criteria**

- 격자가 정확히 **4×4**가 아니면 정의된 예외(또는 `Result` 실패)로 거부한다. *(INV-GRID-SIZE)*
- 값 **0**인 칸이 **정확히 2개**가 아니면 예외로 거부한다. *(INV-EXACTLY-TWO-ZEROS)*
- **0을 제외한** 칸에 **같은 숫자가 두 번 이상** 나오면 예외로 거부한다. *(INV-NO-DUP-NONZERO)*
- 어떤 칸의 값도 **{0} ∪ {1..16}** 밖이면 예외로 거부한다. *(INV-DOMAIN-VALUES)*

---

### Story 2 — 빈칸 탐색

**As a** 학습자  
**I want to** 값이 **0**인 칸의 좌표를 정확히 찾고 싶다  
**So that** 빈칸 순서 규칙에 맞춰 **Solver**가 두 칸에 대한 조합 시도를 할 수 있다  

**Acceptance Criteria**

- 두 빈칸을 **행 우선(row-major)** 순서로 정렬해 반환한다(동일 행이면 열 오름차순). *(출력 계약의 빈칸 순서와 일치)*
- 불변조건이 통과한 입력에 대해 **정확히 2개**의 `(row, col)`(또는 도메인 `Cell`)을 반환한다.
- 내부 표현이 0-index이든, 출력 직전에만 1-index로 바꾸든 **문서·테스트와 한 가지 규칙**으로 통일한다.

---

### Story 3 — 누락 숫자 탐색

**As a** 학습자  
**I want to** 격자에 없는 **1~16** 중 누락된 **두 수**를 알고 싶다  
**So that** 두 빈칸에 넣을 후보 집합이 확정되고 **Solver**가 두 배치만 시도하면 된다  

**Acceptance Criteria**

- {1..16}에서 격자에 이미 등장한(0 제외) 수를 제외했을 때 **남는 수가 정확히 2개**인 경우에만 성공한다.
- 반환 형식은 **오름차순** `(min, max)` 또는 동등한 명명 `(smaller, larger)`로 고정한다.
- 누락이 2개가 아닌 비정상 입력은 상위에서 거절되었거나, 도메인 규칙에 따라 명시적 실패로 처리한다.

---

### Story 4 — 마방진 판정

**As a** 학습자  
**I want to** **0이 없는** 완전히 채운 4×4가 마방진인지 판정하고 싶다  
**So that** **Solver**가 각 조합이 유효한 해인지 판단할 수 있다  

**Acceptance Criteria**

- **모든 행**의 네 칸 합이 서로 같다.
- **모든 열**의 네 칸 합이 서로 같다.
- **두 주대각선**의 합이 위 행·열과 동일하다.
- (프로젝트 계약에 맞춘다면) **1~16이 각각 정확히 한 번** 쓰였는지도 함께 검사한다. *(INV-PERMUTATION-WHEN-FILLED 등)*
