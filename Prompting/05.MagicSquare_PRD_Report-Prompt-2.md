## 정리

- **반드시**: 문제·목표·범위·핵심 동작(입출력·예외)·누구를 위한 것인지.  
- **강하게 권장**: 용어, 성공/품질 기준, NFR, AC·예시, 다른 문서와의 맵.  
- **선택**: 로드맵, UI 상세, 통합 상세, 경쟁 분석, 변경 이력.

현재 `PRD.md`는 필수·권장 대부분을 이미 갖추고 있고, 통합·데이터는 의도적으로 “선택”으로 두신 상태라 구조도 타당합니다. 보강한다면 **가정·리스크·오픈 이슈** 정도만 짧게 추가해도 협업 시 도움이 됩니다.

슬라이드에 나온 구조(UX Contract로 UI의 RED, Logic Rule로 도메인·경계의 RED, GREEN/REFACTOR는 같이 간다 + 3단 매핑표)는 **MLOps와도 잘 맞는다**고 보면 됩니다. 다만 “Dual”을 그대로 두고 MLOps를 **어디에 끼워 넣을지**만 정리해 두는 게 좋습니다.

## 잘 맞는 이유

- **UX Contract**는 그대로 확장됩니다. 예: 추론 중 스피너·“모델 사용 불가”·신뢰도/경고 문구·빈 결과 등은 전부 *보인다/안 보인다*, *가능/불가*로 쓰면 슬라이드의 언어와 동일합니다.
- **Logic Rule** 쪽에 ML이 들어가면, “허용/거부·반환/차단”이 **데이터 스키마 검증 → 전처리 → 추론 → 후처리**로 자연스럽게 이어집니다. TDD의 RED는 “스키마 깨짐”, “임계값 미달”, “타임아웃” 같은 **규칙·계약**으로 잡기 좋습니다.
- **3단 매핑표**에 열을 하나 더 두거나 행을 나누면 됩니다. 예: `Scenario | UX Contract | Logic Rule | MLOps 관측/게이트`(데이터 버전, 모델 버전, 메트릭 임계값, 배포 전 스모크).

즉, MLOps는 “세 번째 UI”가 아니라 **Logic 트랙의 재현성·배포·관측**을 담당하는 층으로 두는 편이 Dual-Track 철학과 덜 충돌합니다.

## 정리하면 추천 구조

| 층 | 역할 | TDD에서 RED의 재료 |
|----|------|---------------------|
| UI | Boundary, UX Contract | 디자인·접근성·상태 문구 |
| Logic | Control + Entity (+ ML 어댑터) | 비즈니스 규칙, 입출력 계약 |
| MLOps | 데이터·학습·평가·서빙·모니터링 파이프라인 | “이 데이터면 실패”, “이 메트릭 미만이면 배포 거부” 같은 **파이프라인/게이트 계약** |

UI는 여전히 “사용자에게 무엇이 보이는지”, Logic+MLOps는 “무엇이 허용되고 무엇이 반환·차단되는지”로 나누면 슬라이드 6.2와 같은 매핑을 유지할 수 있습니다.

## 실무에서의 함정 (짧게)

- **트랙을 너무 많이 쪼개면** 테스트 소유권이 흐려집니다. “UI / Logic(+ML 포트) / 파이프라인 CI” 정도로 역할만 명확히 하는 게 낫습니다.
- ML은 **비결정성·외부 의존**이 있으므로, Logic RED는 가능하면 **결정적인 단위(전처리, 스키마, 후처리, 모킹된 추론 결과)**에 두고, 실모델·드리프트는 **별도 계약 테스트나 평가 잡**으로 두는 식이 Dual-Track과 잘 맞습니다.
- Magic Square PRD처럼 “학습용·계약 우선”이면, MLOps는 처음부터 전부 넣기보다 **데이터/모델 버전 고정 + 한두 개 게이트(스키마, 스모크 추론)**부터 매핑표에 넣는 방식이 부담이 적습니다.

**요약**: Dual-Track은 그대로 두고, MLOps는 **Logic 규칙과 파이프라인 게이트를 같은 “Rule 언어”로 서술**하고, UI는 **그 결과를 어떻게 보여줄지 UX Contract로만** 묶으면 방향이 맞습니다. 원하시면 지금 프로젝트(4×4 마방진) 기준으로 “가짜 ML 포트” 한 개 넣은 매핑표 예시 행만 짧게 적어 드릴 수 있습니다.

|------|-----------|------|

## D. MLOps — PRD에 맞게 “붙이는” 위치

현재 본문에 **이름으로 MLOps는 없음**. 대신 아래를 **MLOps 트랙(또는 게이트)**으로 묶으면 기존 문장과 모순 없이 확장됩니다.

| PRD 원문 | MLOps로 읽는 역할 |
|-----------|-------------------|
| §2.2 결정성, §10 NFR 결정성 | 파이프라인·추론도 **동일 입력→동일 산출**(시드·버전 고정)을 **게이트**로 둘 수 있음. |
| §7 데이터·통합 | **데이터/아티팩트 재현**: InMemory → JSON 어댑터 = **로컬 아티팩트 저장**에 해당; 버전 메타(선택) 추가 시 **실험 추적**으로 확장. |
| §10 테스트·커버리지 | CI에서 pytest = **연속 통합**; 커버리지 임계 = **품질 게이트**. |
| §10 관측성 | `logging` 등 = **서빙/배포 후 관측**의 최소 형태. |
| §2.3 비우선 | “온라인 배포” 비우선이므로 MLOps는 **풀 클라우드 MLOps**가 아니라 **재현성·CI·저장 포트** 수준부터 명시하는 것이 PRD와 일치. |

**아직 PRD에 없고, MLOps를 진지하게 넣을 때만 보강하면 좋은 것:** 데이터/모델(또는 solver 바이너리) **버전 ID**, 평가 메트릭 **임계값으로 배포 거부**, 스모크 추론(또는 golden fixture) **파이프라인 단계**. 이 프로젝트는 솔버가 결정론적이므로 “모델” 자리에 **검증된 fixture 세트**를 두는 식이 자연스럽습니다.

## E. 3단 매핑 (예시 — PRD 시나리오를 표로만 재표현)

| 시나리오 (PRD) | UX Contract (Boundary) | Logic Rule (Control+Entity) | MLOps/게이트 (확장 슬롯) |
|----------------|------------------------|-------------------------------|---------------------------|
| 격자 크기·빈칸·값 위반 | 해당 오류 표시 **가시** (코드·문구 고정 §4.5) | 솔브 **중단**, 경계 **반환** | CI: 해당 계약 테스트 **통과** 필수 |
| 도메인 솔브 불가 | “불가” 계약 메시지 **가시** | 두 배치 모두 불가 시 **반환** | golden case 회귀 **통과** |
| 정답 경로 (§9 fixture) | 성공 피드백 **가시** (UI 정의 시) | `int[6]` **반환** | fixture 버전과 산출 **고정** |
| 마지막 입력 저장 (§7) | (선택) “저장됨” **가시** | **저장** 호출은 Control | 저장 스키마·파일 **버전** 기록(선택) |

## F. 나머지 섹션 — 트랙에 걸치지 않는 공통층

- **§1** 배경·비전 → 전체 프레이밍; §1.2에 “UI + Logic Dual-Track” 문구를 슬라이드 표현으로 한 줄 보강 가능.  
- **§2.1~2.3** 목표·범위 → 두 트랙 + MLOps 범위(지금은 로직·CI 중심)를 한 번에 제한.  
- **§10** NFR → Logic + MLOps 공통.  
- **§11~12** 추적성·용어 → 세 트랙 모두가 참조하는 **사전·맵**.

## G. 한 줄 요약

- **지금 PRD**는 이미 **Logic 트랙(도메인·계약·INV·ECB)**과 **UI 트랙의 최소 형태(경계 실패·Prompting 동기)**를 갖추었고, **MLOps**는 §7·§10·결정성을 **“재현성 + CI 게이트 + (선택) 아티팩트 버전”**으로 이름 붙이면 Dual-Track 프레임 안에 깔끔히 들어갑니다.

## 1. 전체 판정

문서는 **Logic 트랙(도메인·계약·INV·ECB)**을 중심으로 잘 서 있고, **Dual-Track**은 §1.2·§2.1에서 “도메인 트랙 + 경계 계약 트랙”으로 이미 명시되어 있습니다. 다만 슬라이드에서 말하는 **“UI 트랙 = UX Contract로 RED”**와 **“MLOps = 파이프라인·게이트·아티팩트”**는 이름과 목차로는 분리되어 있지 않고, **Logic·경계 쪽에 흡수**된 형태입니다.

---

## 2. 트랙별 매핑 (무엇이 어디에 해당하는지)

### Logic 트랙 (Control + Entity, Logic Rule)

| PRD 위치 | 분석 |
|----------|------|
| §4.1~4.4 | 입력·출력·빈칸 순서·솔브 절차가 **Logic Rule**로 고정되어 있고, 검증 실패 시 Entity로 넘기지 않는다는 점이 명확합니다. |
| §5 | INV-*가 **RED의 근거(규칙 카탈로그)** 역할을 합니다. |
| §6 | ECB·TDD 사이클이 Logic/경계 구현의 **구조적 제약**입니다. |
| §8~9 | 스토리·fixture가 **수용 기준 ↔ 테스트**로 이어지기 좋게 요약되어 있습니다. |
| §2.2 | 도메인 커버리지·입력 경계 테스트·INV↔테스트 매핑은 **Logic 트랙 성공 지표**에 해당합니다. |

**강점:** 계약이 수치·자료형·순서까지 구체적이라, “규칙으로 RED”를 만들기에 충분합니다.

### UI 트랙 (Boundary, UX Contract)

| PRD 위치 | 분석 |
|----------|------|
| §4.5 | `code` + 고정 `message`, Prompting·Report와 동기 → **UX Contract / API 표면 계약**의 정본으로 읽을 수 있습니다. |
| §1.1, §2.3 | 화면보다 계약 우선, UI 화면 품질 비우선 → **UI 트랙의 범위가 의도적으로 얇음**이 문서화되어 있습니다. |
| §3 | 사용자가 “경계·계약 습관”을 목표로 함 → Boundary 중심 학습과 정합적입니다. |

**간극:** 슬라이드처럼 “렌더 직후 오류 없음”, “특정 상태에서 버튼 활성/비활성” 같은 **가시성·상태 기술**은 PRD 본문에 없고, §4.5·외부 문서에 위임되어 있습니다. Dual-Track **UI**를 PRD 안에서만 완결하려면 한 단계 얇은 **UX Contract 표(시나리오 × 보임/안 보임)**가 없습니다.

### MLOps 트랙 (재현성·CI·아티팩트·관측)

| PRD 위치 | 분석 |
|----------|------|
| §10 결정성 | ML이 아니어도 **파이프라인 결정론**과 같은 요구로 확장 가능합니다. |
| §10 테스트·커버리지 | **CI 품질 게이트**의 근거가 됩니다. |
| §7 | 저장소·JSON 어댑터·재현 목적은 **데이터/아티팩트 계층**의 씨앗에 해당합니다. |
| §10 관측성 | 운영·서빙 시 로깅 원칙의 최소 형태입니다. |
| §2.3 | 온라인 배포 비우선 → **풀 스택 MLOps는 범위 밖**이고, “로컬 CI + 재현” 수준과 맞습니다. |

**간극:** “MLOps”라는 용어, **실험/모델(또는 golden fixture) 버전**, **배포 전 스모크 단계** 같은 문장은 없습니다. 지금 문서만 보면 MLOps는 **읽히기는 하지만 이름 붙이지 않은 NFR+§7 조합**입니다.

---

## 3. 내부 정합성

- **§1.2 “Dual-Track”**과 **§2.1-2**, **§6 ECB**는 같은 이야기(경계 ↔ 도메인)를 가리킵니다.
- **§4.4-1**(검증 실패 시 솔브 미진행)과 **§5**, **§8 첫 행**은 서로 모순 없이 맞물립니다.
- **§4.5**가 Report/Prompting과 단일 해석을 요구하므로, **UI/Boundary 계약의 단일 정본** 역할을 합니다.

**용어 측면:** 비전에서는 “Dual-Track TDD”, 본문에서는 “도메인 트랙 + 경계 계약 트랙”이라 **UI**라는 단어는 거의 없습니다. 컨셉 정리에서는 “경계 = UI/API 표면”으로 읽으면 되고, PRD만 읽는 사람에게는 **“UI 트랙”이 경계·Prompting 동기를 뜻한다**는 한 줄이 있으면 해석 비용이 줄어듭니다.

## 4. 요약 표 (컨셉 대비 충실도)

| 층 | PRD 반영도 | 한 줄 |
|----|-------------|--------|
| Logic | 높음 | §4~6, §5, §8~9가 핵심 축으로 잘 잡혀 있음. |
| UI (UX Contract) | 중간 (얇게 의도) | §4.5·외부 문서가 계약 정본; PRD 안 시각/상태 매핑 표는 없음. |
| MLOps | 낮음~중간 (암시) | 결정성·pytest·저장·로깅으로 씨앗만 있음; 파이프라인·버전·게이트 명시 없음. |

## 5. 결론

`PRD.md`는 **Dual-Track의 Logic 쪽과 “경계 계약” 쪽**에 무게가 실려 있고, 그 덕분에 **TDD·INV·입출력 계약**이 한 문서에서 끊기지 않습니다. 정리해 둔 **Dual-Track UI + Logic + MLOps** 관점에서 보면, **UI는 “계약 동기 + 비우선 범위”로 일관**되지만 **UX Contract 언어의 표 형식**은 PRD에 아직 없고, **MLOps는 NFR·데이터 절에 녹아 있을 뿐 명시적 트랙으로는 분리되지 않았습니다.**  

분석만 요청하셨으므로 파일은 수정하지 않았습니다. 원하시면 위 간극을 메우는 **짧은 §(예: 1.2 보강 + 매핑 소절 + MLOps 범위 한 단락)** 초안을 `PRD.md`에 맞춰 문장 수준으로 제안할 수 있습니다.
