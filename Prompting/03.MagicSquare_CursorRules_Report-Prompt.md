---

### 1. YAML 문법 오류

- **구문상 문제 없음**: 최상위 키(`project:`, `code_style:` 등)는 값이 비어 있어도 `null`로 해석되는 일반적인 YAML입니다.
- **`tdd_rules`**: 들여쓴 스칼라 3개는 유효한 매핑입니다. 한글·쉼표만 있는 한 줄 문자열이라 따옴표 없이도 무난합니다.
- **구분선**: `#`만 있는 줄은 전부 주석이라 YAML 파서에 영향 없습니다.

원하면 로컬에서 한 번만 확인하려면: `python -c "import yaml; yaml.safe_load(open('.cursorrules',encoding='utf-8'))"` 같은 방식이면 됩니다.

---

### 2. 누락된 필수 섹션

- Cursor는 **고정된 필수 키 집합을 요구하지 않습니다**. 지금 파일은 사용자가 정의한 8개 키가 모두 있습니다.
- 다만 **실질적으로 “비어 있는” 섹션**이 7개(`project`, `code_style`, `architecture`, `testing`, `forbidden`, `file_structure`, `ai_behavior`)라서, 규칙으로서의 효과는 거의 `tdd_rules`에만 있습니다. “필수”를 **프로젝트가 스스로 정한 최소 가이드**로 본다면, 나머지를 채우지 않은 상태는 **의도적 뼈대**이지 문법 누락은 아닙니다.

---

### 3. `tdd_rules`와 `forbidden` 간 충돌

- **`forbidden`이 비어 있어** 문서 상 **직접적인 문구 충돌은 없습니다**.
- 나중에 `forbidden`에 예를 들어 “테스트 없이 구현만”, “실패하는 테스트 두지 말 것”, “리팩터링 금지” 같은 항목이 들어가면 **`green_phase` / `red_phase` / `refactor_phase`와 논리적으로 충돌**할 수 있습니다. 지금 시점에서는 **충돌 없음**, 다만 **확장 시 교차 검토**가 필요합니다.

---

### 4. Cursor AI가 실제로 따르기 어려운 `ai_behavior`

- **`ai_behavior`가 비어 있어** “따를 수 없는 규칙”은 아직 없습니다.
- 같은 파일을 앞으로 채울 때 피하면 좋은 예:
  - **에이전트가 검증할 수 없는 것**: “항상 로컬에서 전체 테스트 실행 후에만 커밋”, “CI 녹색일 때만 답변” 등 (환경·권한·실행 여부를 모델이 보장하기 어렵습니다).
  - **모호한 의무**: “가능한 한”, “적당히”만 있고 성공 조건이 없는 문장.
  - **도구 없이는 불가능한 것**: 특정 대시보드·슬랙·내부 URL만 보고 판단하라는 식의 규칙.

정리하면, **현재 파일은 YAML·섹션 구성·규칙 간 충돌 측면에서 안전한 초안**이고, 효과를 높이려면 빈 섹션을 채우고 `forbidden`과 `tdd_rules`를 함께 쓸 때는 문장을 맞춰 주는 것이 좋습니다.

**Cursor**

프로젝트 맥락을 확인한 뒤 `.cursorrules` 전체를 작성합니다.



전체 `.cursorrules` 작성 및 저장 중입니다.



한국어 표기를 자연스럽게 수정합니다.



`c:\DEV\MagicSquare_XXX\.cursorrules`에 반영해 두었고, 아래가 전체 내용입니다.

```yaml
################################################################################################
project:
  name: MagicSquare
  summary: 4×4 마방진 퍼즐(빈칸 2개) 입력·출력 계약을 만족하는 ECB 구조의 Python 프로젝트.
  domain: |
    4×4 정수 격자(0=빈칸), 빈칸 정확히 2개, 1~16 및 도메인 불변조건(INV-*) 준수.
    출력은 계약된 int[6] 형식(1-index 좌표 및 두 누락 수 배치 규칙)을 따른다.
  goals:
    - TDD로 레이어 경계·계약 테스트를 우선 고정한다.
    - 알고리즘 복잡도보다 레이어 분리, 리팩터링, 테스트 가독성을 우선한다.
  references:
    - Report/01.MagicSquare_ProblemDefinition_Report.md
    - Report/02.MagicSquare_CleanArchitecture_TDD_Design_Report.md

################################################################################################
code_style:
  python_version: "3.10+"
  style_guide: PEP8 엄격 준수
  type_hints: 모든 함수 파라미터와 반환값에 필수
  docstring: Google 스타일, 모든 public 메서드에 필수
  max_line_length: 88

################################################################################################
architecture:
  pattern: ECB (Entity–Control–Boundary) 3레이어
  layers:
    boundary:
      role: 외부 입출력 담당 (UI, API, CLI)
      responsibility:
        - 사용자·외부 시스템과의 I/O, DTO/프레젠테이션 변환
        - control에 유스케이스 호출만 위임하고 도메인 규칙을 포함하지 않는다
    control:
      role: 비즈니스 유스케이스·애플리케이션 흐름 담당
      responsibility:
        - entity를 조합해 시나리오(검증, 솔브, 출력 변환)를 오케스트레이션한다
        - 경계에서 받은 입력을 도메인 객체로 정규화하고 결과를 반환한다
    entity:
      role: 도메인 데이터 및 규칙 담당
      responsibility:
        - Grid, Cell, Solution 등 값 객체·도메인 서비스·불변조건 검증
        - 프레임워크·I/O·표현 형식에 의존하지 않는 순수 도메인 로직
  dependency_direction: |
    boundary → control → entity (단방향).
    entity는 control·boundary를 참조하지 않는다.
    control은 entity만 참조하며 boundary 타입에 의존하지 않는다.
    boundary는 control(인터페이스/유스케이스)에만 의존한다.

################################################################################################
tdd_rules:
  red_phase:
    description: 실패하는 테스트를 먼저 작성해 요구사항·계약을 실행 가능한 명세로 고정한다.
    rules:
      - 새 동작·버그 수정마다 테스트를 먼저 추가한다.
      - 테스트는 Arrange–Act–Assert 구조와 명확한 실패 메시지를 갖는다.
      - 구현 전에 테스트 실행으로 실패(RED)를 확인한 뒤에만 GREEN으로 넘어간다.
    must_not:
      - 프로덕션 코드를 먼저 작성하거나 테스트 없이 구현을 넓히지 않는다.
      - 의미 없이 통과하는 가짜 테스트(고정 반환만 등)로 GREEN을 속이지 않는다.
  green_phase:
    description: 방금 추가한 테스트를 통과시키기 위한 가장 단순한 구현만 한다.
    rules:
      - 실패한 테스트를 통과시키는 데 필요한 최소 변경만 한다.
      - ECB 경계와 공개 API 계약을 깨지 않는 범위에서만 수정한다.
    must_not:
      - 이 단계에서 구조 리팩터링·중복 제거·이름 변경 등을 하지 않는다.
      - 범위를 넘는 기능 추가나 “미래 대비” 코드를 넣지 않는다.
  refactor_phase:
    description: 테스트가 모두 녹색인 상태에서 동작을 바꾸지 않고 설계를 개선한다.
    rules:
      - 테스트 스위트를 자주 실행하며 작은 단계로 리팩터링한다.
      - public 계약과 도메인 불변조건은 유지하거나 테스트로 보강한다.
    must_not:
      - 새 요구사항이나 버그 수정을 같은 커밋/같은 단계에서 섞지 않는다.
      - 커버리지·계약 테스트를 깨뜨리거나 삭제해 녹색만 유지하지 않는다.

################################################################################################
testing:
  framework: pytest
  pattern: AAA (Arrange-Act-Assert)
  coverage_minimum: "80%"
  fixture_scope: |
    기본은 function 범위. 모듈/세션/클래스 스코프는 비용이 큰 공유 자원이 있고
    테스트 간 누수·순서 의존이 없음이 문서화된 경우에만 사용한다.
    autouse는 최소화하고, 필요 시 이름과 용도를 fixture docstring에 적는다.
  naming_convention: 테스트 모듈·함수·메서드는 test_ 접두사 필수

################################################################################################
forbidden:
  - pattern: 디버깅·로깅 목적의 print() 호출
    reason: 표준 출력에 의존하면 테스트·로그 수집이 불안정하고 ECB 경계 책임이 흐려진다.
    alternative: logging 모듈과 구조화된 로거, 또는 테스트에서는 capsys/assert만 사용한다.
  - pattern: 매직 넘버·문자열 등 의미 없는 하드코딩 상수
    reason: 도메인 의미(예 4, 16, 매직 합)가 코드 곳곳에 흩어져 불변조건 변경 시 오류가 난다.
    alternative: entity 모듈의 명명된 상수·Enum·설정 객체로 모으고 한곳에서만 정의한다.
  - pattern: except 단독 사용 (except: 또는 except Exception: 남용)
    reason: 예외 종류를 숨겨 원인 파악이 어렵고 실패를 삼켜 계약 위반을 만든다.
    alternative: 구체적 예외 타입을 잡고, 불가능하면 except Exception에도 raise 체인·재전파 정책을 둔다.

################################################################################################
file_structure: |
  # magic_square/                    # 패키지 루트 (예시)
  # ├── boundary/                  # UI, HTTP/CLI 어댑터, 입출력 DTO
  # │   ├── __init__.py
  # │   └── ...
  # ├── control/                   # 유스케이스, 애플리케이션 서비스
  # │   ├── __init__.py
  # │   └── ...
  # ├── entity/                    # 도메인 모델·값 객체·도메인 서비스
  # │   ├── __init__.py
  # │   └── ...
  # └── tests/                     # pytest, mirror 구조 권장
  #     ├── boundary/
  #     ├── control/
  #     └── entity/

################################################################################################
ai_behavior:
  before_coding:
    - 관련 테스트 파일(tests/ 및 대상 모듈)을 열어 기존 계약·케이스를 확인한다.
```
